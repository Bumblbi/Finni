# 3. Самая большая проблема — frontend и backend живут разными жизнями

Это первое, что я бы исправлял.

Например, frontend считает стартовый доход:

```text
INITIAL_INCOME = 500
```

и хранит баланс локально. 

При этом серверная экономика определяет другой сценарий дохода.

В итоге получается примерно:

```text
                 ┌───────────────┐
                 │   Backend     │
                 │ authoritative │
                 └───────┬───────┘
                         │
                         │
                 ┌───────▼───────┐
                 │     Sync      │
                 └───────┬───────┘
                         │
                 ┌───────▼───────┐
                 │    Mobile     │
                 │ local stores  │
                 └───────────────┘
```

Но mobile после синхронизации **не применяет весь `state`, который вернул сервер**.

Sync обновляет фактически только `revision` и `epoch`, после чего очищает очередь. 

Это очень серьёзная архитектурная проблема.

### Что может произойти

Например:

1. ребёнок покупает товар;
2. frontend уменьшает локальный баланс;
3. команда уходит на backend;
4. backend рассчитывает своё состояние;
5. backend возвращает новый `state`;
6. frontend этот state почти полностью игнорирует.

В результате:

**сервер думает одно → приложение показывает другое.**

Для обычной разработки это неприятно.

Для хакатона это опасно, потому что эксперт может пройти сценарий и обнаружить несоответствие баланса, накоплений, периода или стадии питомца.

# 4. Ещё серьёзнее: накопления фактически не являются законченной механикой

ТЗ организаторов прямо требует:

* выбрать финансовую цель;
* увидеть стоимость;
* видеть накопленную сумму;
* регулярно переводить деньги в накопления;
* иметь возможность снять деньги после отдельного подтверждения.



На backend это уже предусмотрено:

* `/savings/deposit`;
* `/savings/withdraw`;
* `/goal`. 

Но в mobile я не вижу законченного пользовательского экрана/сценария для этого.

В навигации есть:

* Dashboard
* Budget
* Shop
* Quests
* Parent

но отдельного Savings/Goal экрана нет. 

При этом локальный store имеет `addToSavings`, но это просто изменение локального числа. 

### Поэтому сейчас фактически отсутствует центральная механика:

**«Я хочу накопить → выбираю цель → откладываю → вижу прогресс → могу продолжить или снять часть денег».**

А это одна из центральных частей ТЗ.

# 6. Квесты: количество есть, механика не полностью соответствует ТЗ

Здесь хорошая ситуация с количеством.

В каталоге:

* 2 задания по budget;
* 2 по needs;
* 2 по savings.

Итого **6 заданий по 3 темам**. 

Это полностью соответствует минимальному количеству контента:

> не менее 6 заданий по 3 темам. 

Но есть важный нюанс.

Организаторы специально написали:

> задания не должны ограничиваться выбором ответа из предложенных вариантов.

А текущие задания построены именно как:

```text
Вопрос
↓
вариант A
вариант B
↓
правильный / неправильный
```

То есть по **количеству** всё хорошо, но по **типу игровой механики** есть несоответствие.

### Что сделать

Хотя бы 2–3 задания переделать в интерактивные действия.

Например:

**Задание «Составь бюджет»**

У ребёнка:

```text
100 монет

🍎 Еда       30
🎮 Игрушка   40
🐷 Копилка   20
```

Нужно самостоятельно распределить деньги.

Или:

**«У тебя осталось 35 монет»**

Нужно перетащить покупки в корзину:

```text
Еда          20
Вода         10
Игрушка      30
```

И ребёнок сам принимает решение.

Так вы будете реально соответствовать принципу «обучение действием», а не просто викторине.

# 13. API URL сейчас не готов для физического Android

Сейчас:

```text
http://localhost:8080/api/v1
```

Причём комментарий прямо говорит, что для физического устройства нужен IP компьютера, но фактически оставлен localhost. 

На физическом Android:

```text
localhost
```

будет означать **сам телефон**, а не ваш компьютер.

Следовательно, backend на физическом устройстве сейчас нормально не заработает без дополнительной настройки.

Для финальной сборки надо сделать конфигурацию:

```text
API_URL
```

через environment/build config:

```text
development emulator
→ 10.0.2.2

physical device
→ IP компьютера / HTTPS сервер

production
→ production HTTPS endpoint
```

Их надо убрать.

```text
15. Повторный запуск
        ↓
16. Родительский раздел
        ↓
17. Reset
```

Именно этот путь эксперт должен суметь пройти без объяснений разработчика.

```text
 ↓
```

будут одной непрерывной цепочкой.

**Вот это сейчас нужно сделать.**

**«ТЗ организаторов × твоё ТЗ × текущий код»**

* 🟢 реализовано;
